## 一、建议项被当强制扣分项 → 引入「建议项」判定档

### 机制
系统状态枚举仍是 `Pass / Fail / Review`（后端 `ReviewResultSchema.CHECK_STATUS_ENUM`，未动）。
建议项落在 **`Pass` + 非空 `suggestion`** 上，不写入 `issues`、不计入 `missing_items`。

### 改了什么

| 位置 | 处数 | 内容 |
|---|---|---|
| 全局判定约束（每条规则） | 559 | 新增「**建议项不扣分**」条款：标注「【建议项】」以及以「宜/建议/可/最好」表述的要求，一律不得作为 Fail 或 Review 依据；只有「【强制项】」或以「应/须/必须/不得」表述并给出明确阈值的条款才可判 Fail |
| 逐条改写「宜」类条款 | 84 | 见下 |
| 提示词输出契约 | 104 | 原文「Pass 时 suggestion 为空字符串」会直接废掉建议项机制，已改为「【建议项】判 Pass 时填写优化建议」；同步补充 4.1 状态归并、4.4 结果一致性、第八节判定表达锚点 5/6 |

### 逐条改写的「宜」类条款
- **替代设备记录要求**（25 个章节文件，原文即用「宜」却产出 Review）→ 建议项
- **一览表引用标准条款列**、**子项顺序一致性** → 建议项（仅精确到章未细到条不再扣分）
- **承试单位资质**、**预处理与恢复条件**、**设备主要参数**、**接口速率**、**构型层次** → 建议项
- **燃料蒸发防凝结**、**盐雾空气源湿度/水温**、**结冰双试验箱**、**结冰温度确定方式** → 未写=建议项，**写了但越限仍判 Fail**（保留技术底线）
- **霉菌强制风速上限** → 未给出风速=建议项；给出且超 1 m/s=Fail
- **试验记录数据条目**、**故障归零机制**、**影像资料**、**报告审批归档**、**记录表格种类**、**故障报告表字段** → 建议项

### 分档口径
- 「宜」+ **完全未提** → 建议项，判 Pass
- 「宜」覆盖的清单 + **条目不全** → 建议项，判 Pass
- 「应/不得」+ **原文已写且违反** → 强制项，判 Fail
- **空泛到不可执行**（如只写「按要求记录」）→ 仍判 Fail，属空泛表述而非建议项

## 二、证据齐备仍判不通过 → 三条全局硬约束

全部 559 处判定约束新增：

**1. 证据充分即通过**
> 证据在数值、时长、次数、状态、顺序、精度上已满足要求时，必须判 Pass。不得以「表述易混淆」「未明确」「未显式说明」为由推翻自己已摘录的证据。原文写「至少 3h」「保持 3h」「稳定后再保持 3h」，规则要求「至少 3 小时」，三者均判 Pass；原文写「不低于 5℃/min」，规则要求「最小 5℃/min」，判 Pass。
> **若 evidence 中已含满足要求的数值或状态，reason 不得出现「未明确」「未给出」「缺少」等与该证据矛盾的表述——出现即为判定错误。**

最后一句直接封死了专家反馈的那个失效模式（自引「至少3h」又写「未明确」）。

**2. 跨章引用视为本章证据**
> 原文以编号、代号或章节号引用本大纲其他章节（如「工作状态1」「详见 6.4 节」「见 8.4」「按 12.2 章节表 12 要求」），必须先解析被引用处再判定。被引用处已给出所需内容的，视为本章已满足，判 Pass。仅当被引用目标不存在、指向错误或内容为空时才判 Fail，且定位到被引用处，同一缺陷不在各引用章重复报告。

**3. 不适用即通过**
> 条款适用范围由设备类别、供电制式、安装区域、试验方法限定时，先判适用性再判符合性。类别落在适用范围之外的判 **Pass** 并写明「本条适用于 X，本设备为 Y，不适用」，既不判 Fail 也不判 Review。

同时清除了规则中残留的「判「不适用」」写法（`05-温度变化` 温度冲击、`02-一览表` 跨章编排子项）——
系统无 N/A 状态，这类写法会被归并成 Review，正是待复核被滥用的来源之一。

## 四、表格解析不足 → 定位到 3 个具体缺陷，已修 2 个

专家原话：「已在表55表述，**建议加强表格识别能力**」「证据已包含16.6.1.3，只是**合并单元格提取错位**」。
排查后确认不是模型能力问题，是解析器的确定性 bug。

### 缺陷 1：合并单元格的覆盖区被清空（已修 + 测试）
`WordParser.expandTableGrid()` 把表格摊平成矩形网格时，被合并覆盖的单元格一律置 `""`：

```java
grid.get(r).set(c, "");   // 覆盖区一律置空
```

送给模型的是这份摊平后的 markdown。于是纵向合并的「试验标准章条」列在第 2 行起变成空白，
模型读到 `| 4 |  | 第16.6.1.3条 | 瞬时电源中断 |` 就报「条款细分号缺失」——而原表里它是有的。
**改为让覆盖区携带合并值**，每一行都能独立对齐表头；HTML 渲染里的 `rowspan/colspan` 仍是原始几何的权威来源。
新增测试 `verticallyMergedCellsKeepTheirValueInEveryCoveredRow`。

### 缺陷 2：附录字母整体偏移（已修 + 验证）
专家：「该部分是**附录B**，表B.1～B.3 编号正确」，而系统标成了附录C／附录D。
两个叠加的错误：

1. **空的分节符段落也在推进附录计数器**。Word 在分节处留下的空段落继承了「附录标识」样式，
   被当成一个附录。已加 `isSectionBreakOnlyParagraph()` 守卫（带 `sectPr` 且无 run 的段落跳过）。
   真正的空附录标记段落带书签、不带 `sectPr`，不受影响。
2. **`setCounter` off-by-one**。`formatNumber` 是先自增后渲染
   （`counters.getOrDefault(key, startVal-1) + 1`），用本附录序号播种计数器会渲染成下一个字母。
   已改为播种 `currentAppendixLetterIndex - 1`。

**实测验证**（`prompts/` 下真实样本，与文档正文实际出现的附录字母逐一核对）：

| 文档 | 修复前 | 修复后 | 文档实际 |
|---|---|---|---|
| 集成式备用仪表（电磁类） | 附录B／附录D | **附录A 检测记录表／附录B 试验故障报告** | A、B ✓ |
| 集成式备用仪表（非电磁类） | 正确 | 附录A／附录B／附录C | A、B、C ✓ |
| 环境鉴定试验大纲模板（电磁类／非电磁类） | 正确 | 附录A／附录B | A、B ✓ |

### 缺陷 3：`appendixStyleHasOwnNumbering` 把样式 ID 硬编码为 `"120"`（**未修，仅记录**）
`WordParser.java` 判断附录样式是否自带编号时只查 `styles.getStyle("120")`。
集成式电磁类文档的附录样式 ID 是 `"58"`（且自带 numId=6），查不到就走了手动计数分支——
这正是缺陷 1、2 在该文档上暴露出来的原因。
改成按样式名查找会**切换多数文档的代码路径**，风险面远大于收益；当前两条分支都已能给出正确字母，
故只记录不改。若后续要改，需对全部样本重跑附录字母比对。

## 五、R-Q 文字质量规则优化方案（已实施）

R-Q 是单规则误报第一（80 条误报中占 12 条）。原因是三条检查项的通过标准只是问题的同义反述，
没有任何判定边界。方案分四层，写入 `backend/src/main/resources/schema.sql`：

**第 1 层 举证门槛** —— 报出任何文字问题必须同时给出三项，缺一即判 Pass：
① 含问题的完整句子逐字摘录；② **改正后的完整句子**（不接受「建议修改」「统一表述」这类空话）；
③ 改正前后的工程含义、数值、类别、指代对象完全一致。
改正会改变工程含义的（如把「测试设备」改成「试验设备」），说明不是文字问题。

**第 2 层 豁免清单** —— 六类一律不报：
引自标准原文的表述（含数值格式与标点，如「15，000.3，000 个孢子/平方厘米」）、
脱密占位符 XXX、航空与试验领域专业术语与固定搭配（「直流搭接电阻」等）、
标题与正文的用词差异、格式类差异、标准中本就存在的多种合规写法。

**第 3 层 术语一致性判定方法** —— 必须同时满足三条才判不通过：
a. **先证明两个词同指**（同一表格同一列、同一句并列、或显式定义为同义），不能证明的判 Pass；
b. 明确列出**不是术语不一致的词对**：`测试设备≠试验设备`、`受试设备≠陪试设备`、
   `试验程序≠试验方法`、`检查≠检测`、`校准≠校验≠检定`；
c. 差异须在同一章节内，引用其他章节时沿用原词不算不一致。

**第 4 层 置信度门控** —— 需要推测作者意图、需联系上下文才成立、或与豁免清单沾边的判断一律 Pass。
**本规则不产生 Review 结果。**

三条检查项的 `pass_criteria` 同步重写，并新增 `UPDATE` 语句刷新存量库
（原 seed 是 `WHERE NOT EXISTS`，已部署环境拿不到新文案）。
已对运行中的 `ai-review-db` 实测执行（`ON_ERROR_STOP=1` 无报错），R-Q 内容与三条检查项均已更新。
