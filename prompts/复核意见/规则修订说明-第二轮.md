# 规则修订说明（第二轮）

数据来源：`审查意见_红标件环境试验大纲样例（通用章节+温度高度+霉菌+磁效应+电源输入）-Deepseek-V4-FlashLBin.xlsx`
（84 行：不通过 51 / 通过 22 / 待复核 11；人工复核 57 条 √）。

这份文件与已有的两份「红标件（全量规则）」构成**受控对照**——同一份大纲、同一个模型（DeepSeek），只有规则范围不同。

## 一、专家疑问的结论：不是模型不稳定，是两次审查用的根本不是同一套规则

### 1.1 先看直接证据：同一检查项，两次运行看到的原文不同

| 检查项 | 子集版引用的证据 | 全量版引用的证据 |
|---|---|---|
| `04-01` 设备名称型号 | 只有表头 `\| 序号 \| 设备名称 \| 用途 \|…` | 「快速温变试验箱WD1000C-15、高低温低气压试验箱TD1000C-SP」 |
| `04-02` 设备是否足够 | `\|  \| 综合淋雨试验装置 \| 用于过压试验 \|`（首列空） | 表14 完整用途覆盖 |
| `13-02`/`13-03` 霉菌设备 | 「设备型号 TBD」 | 「霉菌试验箱、钢卷尺、温湿度变送记录仪」「温度偏差±1.0℃」 |
| `GEN-10` 功能检查 | `\| QPAT2-3 \| 内容 \| 检测方法 \|` | 表12 完整三组检查项 |

方向与直觉相反：**不是全量版漏检，而是子集版只读到表头或占位行就下了结论**。
专家自己也标了其中三条：「×，引用了其他文件，**建议增强表格识别能力**」「×，已描述处于非工作状态」。

### 1.2 决定性证据：92% 的检查项连题目都不一样

对 72 个两次都出现的 `check_code` 逐条比对「检查项」文字：

| | 条数 | 两次运行判定一致率 |
|---|---|---|
| 检查项文字**相同** | 6 | **83%**（5/6） |
| 检查项文字**不同** | 66（92%） | **47%**（31/66） |

同一个规则编号，两次问的问题不是同一个。例如：

- `04-13`：子集「冷却能力损失试验**适用性判断**是否充分」／ 全量「飞行中冷却能力损失试验**适用性及参数**」
- `04-15`：子集「减压试验**参数**是否满足要求」／ 全量「减压试验**适用性、起始压力、减压时间和保持时间**」
- `04-06`：子集「设备鉴定类别是否声明且**与安装区域自洽**」／ 全量「是否明确声明设备鉴定类别**且一致**」

**规则文字一致时两次运行有 83% 的一致率；规则文字不同时掉到 47%。分歧由规则内容漂移驱动，不是模型随机性，也不是规则数量多寡。**

### 1.3 根因：规则文件与数据库之间没有同步，也没有校验

规则靠人工上传 `.md` 入库（`POST /api/v1/rules/upload`），`prompts/DO160G规则/` 与库中实际生效的规则之间
**既无自动同步，也无一致性校验**。用新写的核验脚本实测当前环境：

```
规则文件 287 条 ｜ 数据库 133 条 ｜ 交集 74 条
  仅规则文件有 213 条   —— 改这些文件不会影响审查
  仅数据库有    59 条   —— 无法通过改文件维护
  规则名不同    10 条   —— 同一编号指向了不同的规则
  规则名相同但正文不同 64 条
合计 346 处漂移
```

交集 74 条里，**没有一条与规则文件完全一致**。最典型的是 `QTP-GEN-*` 整族被重编过号：

| 编号 | 规则文件 | 数据库（实际生效） |
|---|---|---|
| `QTP-GEN-03` | 通用要求 | 试验连接图与布置图 |
| `QTP-GEN-06` | 设备中文名称 | 试验线缆与电搭接 |
| `QTP-GEN-09` | **设备安装区域** | **试验顺序与试验件安排** |
| `QTP-GEN-10` | 受试设备功能描述 | 设备功能检查与试验前中后检查要求 |

也就是说：**同一个 `QTP-GEN-09`，在规则文件里是「设备安装区域」，在跑起来的系统里是「试验顺序」。**
两次审查之间只要有人重新导入过规则，编号相同的条目就已经换了内容——结果自然不可比。

### 1.4 顺带修正一个说法

专家感受到的「子集发现的很多问题全量没发现」，逐条核对后是：
**14 条**满足「子集判不通过、两个全量都没判不通过」，其中专家标注**真问题 7 条、子集误报 7 条**，正好各半。
同时反向也有 **11 条**是全量判不通过而子集没判。所以这是**双向的**，不是单向漏检。

三方（子集DS／全量DS／全量MM）在 72 个共有检查项上**判定完全一致的只有 22 条（31%）**；
不通过数分别是 **39 / 33 / 18**。

## 二、本轮规则修改

### 2.1 已验证方向正确（上一轮改动已覆盖，本轮无需重复）

新文件里约半数否定意见，恰好落在上一轮已修的点上，可作为上一轮改动的有效性验证：

| 专家意见 | 上一轮对应改动 |
|---|---|
| 「通过，该部分可作为建议项」（`04-05`、`13-05` 替代设备记录，2 条） | 替代设备记录要求 → 【建议项】 |
| 「×」（`16-06`、`16-08` 判 AXI 非法，2 条） | `AXI` 等直流标识合法，判 Pass |
| 「×，已满足要求」「×，已描述处于工作状态」「×，已描述处于非工作状态」（`04-07`~`04-16`，5 条） | 全局「证据充分即通过」 |
| 「通过，无需补充」（`15-09` 不干扰临近设备） | 删除该强制项 |
| 「×，引用了其他文件，建议增强表格识别能力」（`GEN-10`） | 合并单元格摊平 bug 已修 |

### 2.2 本轮新增修改（8 条，全部两处同步，共 571 处）

**全局判定约束新增两条**（覆盖全部 559 处）：

1. **与标准原文一致即通过** —— 大纲表述与 DO-160G 相应条款一致时一律判 Pass，**不得要求大纲比标准更细**。
   标准本身只作原则性规定的（如「必须由**有资质的人员**来进行评价」并未定义何种资质），大纲照搬即合规。
   仅当取值、名称或程序与标准**确有出入**时才判 Fail，且须同时引用标准原文与大纲原文，写明「标准为 X、大纲为 Y」。
   > 对应专家意见：「×，**标准即未明确是何资质**，该描述与标准一致」（`13-10`）

2. **引用本文档表格前必须先读表** —— 原文写「见表 N」「详见附录 X」指向本文档自身表格时，
   必须先定位读取再判定，**不得因正文只写了一句引用就断言其内容缺失或与标准不一致**；
   检索不到时判 Review 而非 Fail。
   > 对应专家意见：「×」（`13-06`，模型仅凭「试验菌种见表68」一句就断言菌种与标准不一致）

**逐条修改 6 处**：

| 规则 | 问题 | 修改 |
|---|---|---|
| `QTP-XREF-09` | **规则自身错别字**：步骤 2 把第 1 章规定名称写成「1 **实验**目的」，模型忠实照报「应为实验目的」 | 改为「1 **试验**目的」，并加注「不是『实验目的』，大纲写『试验目的』即正确」<br>专家：「×，第一章标题正确」 |
| `QTP-DO160G-15-06` | 步骤 1 把「判据区间 D」与「安装距离」写在同一串括号里，模型与专家都读岔 | 拆成两列表格，注明「判定类别只看判据区间 D 这一列，不得拿右列去比对」<br>专家：「通过，但是**规则有误**，Z类：0<D≤0.3」 |
| `QTP-DO160G-13-08` | 模型把对照样品的**正**磷酸二氢钾当成写错了 | 加注区分：对照样品浸渍液用**正磷酸二氢钾**（13.5.4 原文）；**磷酸二氢钾 KH₂PO₄ 0.7g** 是**无机盐溶液**（13.5.1）的成分，两者是不同配方里的不同条目。大纲写「正磷酸二氢钾」即正确<br>专家：「×」 |
| `QTP-DO160G-13-08` 步骤1 | 菌种以表格给出时未要求先读表 | 写出标准的 5 个菌种（黑曲霉 ATCC 9642 等），要求先读表再逐个比对，判 Fail 须写明「标准为 X、大纲为 Y」 |
| `QTP-DO160G-13-06` | 职责越界，拿菌种内容判类别声明 | 限定本规则只判「类别声明与试验/豁免安排」，菌种归 `13-08` |
| `QTP-DO160G-16-09` | 「判据未区分正常/异常工作状态判 Fail」过严 | 改为【建议项】：以统一 QPAT 检查覆盖全部子试验即判 Pass；只有写出与标准**相抵触**的判据才判 Fail<br>专家：「×」 |
| `QTP-XREF-08` 步骤5 | 顺序约束未强制先建立试验件分组 | 改为硬前置：**判定任何顺序违规之前必须先提取并写出试验件分组**；未先确定分组就断言违规属判定错误<br>专家：「×，需结合试验件安排判断，**试验件2在进行完爆炸大气后未进行其他试验**」 |

**内置质量规则 R-Q** 豁免清单新增第 7 条：
「同上」「同前」「见上节」等**承前省略**是中文技术文档的正常引用，不属术语不一致，最多写入 suggestion。
> 对应专家意见：「√，建议补充」（`R-Q-C003` 把试验判据中的「同上」判为术语不一致）
已对运行库实测执行并确认生效。

## 三、针对同步问题的修复

新增 **`tools/check_rule_drift.py`**：比对 `prompts/DO160G规则/*.md` 与数据库中实际生效的规则，
报告「仅文件有／仅库有／同编号不同名／同名不同正文」四类漂移，**有漂移时以退出码 1 结束**，可直接用作发布门禁。

```bash
python tools/check_rule_drift.py
```

```bash
python tools/check_rule_drift.py --scope QTP-DO160G-04 --quiet
```

支持 `--psql`（本机 psql）与 `--scope`（只比对某一族）；数据库连接可用
`AI_REVIEW_DB_CONTAINER` / `AI_REVIEW_DB_USER` / `AI_REVIEW_DB_NAME` 覆盖。

**这只让问题可见，不会自动修复。** 要让本轮及上一轮的规则改动真正生效，必须把规则文件重新导入：
`POST /api/v1/rules/upload`（`replaceExisting=true`），导入后重跑本脚本确认漂移归零。

> **重要提醒**：在重新导入之前，前两轮对 `prompts/DO160G规则/` 与 `prompts/DO160G规则提示词/`
> 的全部改动（累计 1200 余处）**对运行中的系统没有任何影响**——库里跑的仍是旧版判据。
> 只有 `schema.sql` 里的 R-Q 是例外，它由启动脚本自动刷新，已实测生效。
>
> 另外，规则文件的 `QTP-GEN-01~14` 与库中的 `QTP-GEN-01~10` 是两套不同编号方案，
> **重新导入会改变 GEN 族每个编号的含义**。导入前需要先确认以哪一套为准，
> 否则历史审查结果与新结果在 GEN 族上无法按编号对齐。
